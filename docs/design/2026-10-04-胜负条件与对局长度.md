## 1. 三层结束语义（核心）

**设计红线：三种结局在 UI 文案上必须一眼可辨，任何情况下「统一」二字只能出现在真胜利上。**

### 1.1 定义表

| 语义 | 代号 | winner 字段 | `end_reason` | 标题文案 | 副标题文案 | 图标 |
|------|------|------------|--------------|---------|-----------|------|
| **统一（真胜利）** | unification | 胜利势力 id | `"unification"` | 「{势力} **一统天下**」 | 「第 {turn} 回合 · 廓清寰宇」 | 🏆 |
| **时限结束（领先）** | timeout | 领先势力 id（并列必胜出唯一）/ 无则 null | `"timeout"` | 「{势力} **领先胜出**」 | 「第 {turn}/{max} 回合 · **时限已到，天下未定**」 | ⏳ |
| **僵局结束（领先）** | stalemate | 领先势力 id / 无则 null | `"stalemate"` | 「{势力} **领先胜出**」 | 「连续 {N} 回合无战事 · **僵局收束，天下未定**」 | ⚖️ |
| **未分胜负（平局）** | 复用 timeout 或 stalemate | `null` | 同左 | 「天下未定 · 平局」 | timeout→「第 {turn}/{max} 回合 · 时限已到，无人胜出」／stalemate→「连续 {N} 回合无战事 · 僵局收束，无人胜出」 | 🤝 |

> **「出局」（Eliminated）不是终局语义**，它是**势力级状态**，不是对局级结局：某势力 `is_alive=False`（城市数=0）→ 前端排名行打「已出局」标签（`GameOverOverlay.tsx:58` 已实现），但它**不等于对局结束**。对局是否结束由上面三层决定。此二者务必分开叙事，避免"队友出局=我输了"的误读。

### 1.2 统一（真胜利）的严格定义

**推荐定义：统一 = 地图上全部「初始有主城市」归同一势力所有。**

- 判据（字段级）：`{ city.faction | city ∈ cities, city.faction != "neutral" }` 的势为 **1**。
- 该判据**等价于**「所有非中立城只剩一个主人」，但**语义锚点从"相对（对手都没了）"改为"绝对（疆域归一）"** —— 这正是玩家诉求 2 想要的语义修正：不是"别人都没城了所以算你赢"，而是"全国有主之城尽归你"。

#### 为什么是「占领全部非中立城市」而不是「只剩一个势力」

当前代码 `engine.py:1763` 用的是 `len(active_factions) == 1`（"只剩一个势力"）。两者在**结果上高度重合**，但语义与鲁棒性不同。逐条分析边界情况：

| 边界情况 | 「只剩一个势力」的问题 | 「占领全部非中立城市」的处理（推荐） |
|---------|--------------------|--------------------------------|
| **中立城怎么算** | 中立城被 `f != "neutral"` 直接排除，语义上"中立城不属于任何人的胜利拼图"，但定义没明说中立城**能不能被占地**。 | 明确：**中立城不计入统一条件**。开局 31 城 = 21 有主 + 10 中立；统一只需 21 座有主城归一。**不要求**征服 10 座中立城（否则开局先要打 10 场无意义围攻，节奏被拖长）。玩家/LLM 额外打下中立城属于"扩张"，不影响判据。 |
| **有军无城的残军** | "只剩一个势力"以**城市数**计势力存活，"残军"天然不算势力 → 若 A 占满全部有主城，X 尚有 3 支在途军队，A 仍会立即判胜。**这是对的**，但措辞"只剩一个势力"给不出这个结论的直觉解释。 | 明确：**统一只看城市归属，不等残军。** 某势力城池全失但仍有在途军队时，其余势力一旦占满 21 座有主城即宣告统一；残军在下个 `process_turn` 由 `_cleanup_dead_armies`/`_sweep_stranded_armies` 清理，且 `game_over=True` 后不再 `process_turn`，残军自然冻结、不会"复活"建城。 |
| **被围未陷落** | 无区分 → 需在实现层保证"围城不改变 `city.faction`"。 | 明确：**判定一律读 `city.faction`，绝不读 `city.is_besieged`。** 被围（`is_besieged=True`）但守方仍控城的城市，**仍计作守方城市**，不满足统一。只有 `city.faction` 真正改写（占领成功）才算易主。 |
| **有城但被俘虏的势力** | 与本判据无关（城在即算存活）。 | 同左：以城市为准，将领被俘不影响势力是否"在版图上存在"。 |

> **是否要求"额外占领中立城"才叫统一？** 提供两个选项给用户拍板：
> - **选项 α（推荐）**：不要求。统一 = 21 座有主城归一。中立城是甜点不是门槛。
> - **选项 β（更"字面统一"）**：统一 = 地图上**全部 31 城**（含中立）归一。优点是最字面意义的"统一中国"，缺点是终局被 10 场中立城围攻拖长。
> 推荐 α：与实测节奏（历史结论 49 回合起零战斗）冲突最小，且中立城 10 座占比 1/3，要求全占会显著拉长对局。

### 1.3 时限结束 / 僵局结束 = 「领先」，不是「统一」

- **时限结束（timeout）**：`game_mode == STANDARD` 且 `turn >= max_turns` 且**尚未统一** → 结束，`winner = 城市最多者`。
- **僵局结束（stalemate）**：`game_mode == INFINITE`，连续 `N` 回合 `battles_fought == 0`（默认 N=6）→ 结束，`winner = 城市最多者`。
- 两者共用同一套**确定性决胜**（见 §3.3），且 `end_reason` 不同以便文案区分。
- 🔴 **硬约束**：这两种结局的 UI 文案**只能出现「领先 / 胜出 / 天下未定」，绝不允许出现「统一」「一统天下」**。这正是玩家诉求 2 的直接修复点。

## 2. 默认对局长度方案

历史结论（要正面回应）：默认从 192 降到 48 的依据是"实测第 49 回合起零战斗，后 144 回合空转、LLM 成本翻 4 倍"。**该顾虑成立**，所以不能简单"改回无限"就交差 —— 必须给出**在无限模式下也能防空转**的机制。

### 2.1 候选方案

| 方案 | 默认 `game_mode` | 默认 `max_turns` | 优点 | 缺点 |
|------|----------------|-----------------|------|------|
| **A：默认无限（裸）** | infinite | 9999 | 完全满足诉求 1，想打多久打多久 | **直面历史顾虑**：可能重现 144 回合空转烧钱，未解决 |
| **B：默认 192** | standard | 192 | 保留有限时长；192 是历史硬上限 | 实测 49 起零战斗 → 后 143 回合仍空转，成本 4 倍，**等于没解决当初降 48 的问题** |
| **C：默认 48 + UI 明示"领先"** | standard | 48 | 成本最优，改动最小 | 仍是"局限在回合"，**未正面回应诉求 1**，玩家观感=换个说法而已 |
| **A′：默认无限 + 僵局熔断（推荐）** | infinite | 192（作为软上限/兜底） | 有战事就打到统一（满足诉求 1）；零战斗连续 N 回合即收束为「领先」（解决空转成本） | 需新增一个零战斗计数器与一个 `end_reason` 字段（改动可控，见 §4） |

### 2.2 推荐：方案 A′（默认无限 + 僵局熔断）

**设计意图：把"回合上限"从"时间闸"改成"行为闸"。**

- 只要**棋局在推进**（每回合有战斗），就允许一直打到**统一**——直接兑现"不要局限在回合"。
- 一旦进入历史观测到的**"无人再打仗"空转区**，机制在 **N 个回合内**熔断收束为「领先胜出」，而不是傻跑满 192。
- 用实测数据验证收益：历史"第 49 起零战斗"、N=6 → 约第 55 回合熔断，**比跑满 192 省 ~71% 的回合**、比旧默认 48 只多几回合，**画面内容几乎无损**（本就无战斗），却让"有战事的长局"能跑到统一。

**熔断机制（僵局探测）——伪代码级：**

```python
# process_turn() 末尾，在调用 _check_victory() 之前统计
# 复用已有字段：result["battles_fought"]（engine.py:1339 已累计）
if result["battles_fought"] == 0:
    self._consecutive_zero_battle_turns += 1
else:
    self._consecutive_zero_battle_turns = 0

# _check_victory() 内（无限模式分支）
if self.game_mode == GameMode.INFINITE:
    if self._consecutive_zero_battle_turns >= STALEMATE_TURNS:  # 默认 6
        self.game_over = True
        self.winner = self._leading_faction(city_counts)
        self.end_reason = "stalemate"
    return
```

**为什么用 `battles_fought == 0` 而不是别的：**
- 该字段已在引擎内免费产出、已进 `TurnLog`、已进 WS 事件（`game_manager.py:799,825`），**零新增数据采集**。
- "零战斗" именно 命中历史空转的物理表现，判据稳定、可复现（确定性无随机）。

**可调参数（建议，待用户定）：**

| 参数 | 默认 | 说明 |
|------|------|------|
| `GameConfig.game_mode` | `"infinite"` | 默认模式（本次变更点） |
| `GameConfig.max_turns` | `192` | 无限模式下的**软上限/兜底**；达到仍未统一且无僵局 → 也按 timeout 收束（防极端死循环） |
| `STALEMATE_TURNS` | `6` | 连续零战斗回合阈值。历史空转从第 49 起 → 约 55 收束 |

**同时保留快档：** `48` 不作为默认，但作为**可显式选择的"观众短场/压测档"**保留（`run_web.py --max-turns 48`、`GAME_MAX_TURNS=48`），其结束文案同样用 §1.3 的「领先」，绝不叫统一。

## 3. 判定细节（可实现伪代码）

### 3.1 新增状态字段

| 字段 | 位置 | 类型 | 说明 |
|------|------|------|------|
| `end_reason` | engine + `GameState` 模型 + 前端 `types.ts` | `Optional[Literal["unification","timeout","stalemate"]]` | 结局语义；`None` = 未结束 |
| `_consecutive_zero_battle_turns` | engine（私有） | `int` | 僵局计数器，`process_turn` 维护；**不进快照**（可由 TurnLog 重算，不入档更省） |

> `winner` 字段语义不变（为排名/前端保留），新增 `end_reason` 专司"这是哪种结束"。**两字段组合**才能唯一确定 UI 文案。

### 3.2 `_check_victory` 重构意图（伪代码）

```python
def _check_victory(self) -> None:
    if self.game_over:
        return

    # ① 统计城市（含 neutral）
    city_counts = {}
    for city in self.cities.values():
        city_counts[city.faction] = city_counts.get(city.faction, 0) + 1

    owners = [f for f, c in city_counts.items() if c > 0 and f != "neutral"]

    # ② 统一（真胜利）：非中立城只剩一个主人 == 全部有主城归一
    if len(owners) == 1:
        self.game_over = True
        self.winner = owners[0]
        self.end_reason = "unification"
        return
    if len(owners) == 0:                      # 极端：全部城市变中立（正常不会发生）
        self.game_over = True
        self.winner = None
        self.end_reason = "timeout"
        return

    # ③ 无限模式：不因 turn 结束；仅僵局熔断
    if self.game_mode == GameMode.INFINITE:
        if self._consecutive_zero_battle_turns >= STALEMATE_TURNS:
            self.game_over = True
            self.winner = self._leading_faction(city_counts)
            self.end_reason = "stalemate"
        return

    # ④ 标准模式：到软上限 → 领先结束（绝不叫统一）
    if self.turn >= self.max_turns:
        self.game_over = True
        self.winner = self._leading_faction(city_counts)
        self.end_reason = "timeout"
        return
```

### 3.3 领先者判定（保留现有确定性决胜）

抽成 `_leading_faction(city_counts)`，**逻辑与现有 `engine.py:1781-1796` 完全一致**，保证不破坏既有确定性契约（ADR-0002 / 跨进程可复现）：

```
active = {f: c for f, c in city_counts if f != "neutral"}
若 active 为空 → return None
max_count = max(active.values())
winners = [f for f,c in active if c == max_count]
若 len(winners) == 1 → return winners[0]
否则按确定性次级指标降序：
    ① 守军总数 Sum(garrison)  ② 人口总数 Sum(population)
    ③ 总 gold ④ 势力名 faction 字典序（稳定兜底）
```

**确定性要求（不可破坏）：**
- 决胜链**必须**以 `faction` 字典序收尾，保证任意输入都有唯一结果。
- 排序键不得引入集合迭代序 / `dict` 迭代序（Python 3.7+ 插入序虽稳定，但跨进程场景仍需显式排序，参考 ADR-0002 与 `test_cross_process_determinism.py`）。

### 3.4 前端渲染（GameOverOverlay.tsx）— 后端 canonical，前端 verbatim

🔴 **接口已定（主理人拍板 = 方案 ①）**：文案单一真源在**后端** `format_end_copy(...)`（见 §3.6）；前端**不再做任何 `end_reason`→文案 映射**。

后端在 `/api/state` 顶层下发 `end_title` / `end_subtitle` 两个成品字符串，前端 Overlay 直接渲染：

```tsx
// GameOverOverlay.tsx
// 现状 `const reason = state.turn >= state.max_turns ? '回合耗尽' : '一统天下'` —— 删除
// 改为 verbatim 渲染后端成品文案；TS 里不得再出现「一统天下」等文案字面量
const title = state.end_title ?? ''
const subtitle = state.end_subtitle ?? ''
// <div style={styles.headline}>{title}</div>
// <div style={styles.sub}>{subtitle}</div>
```

> 未结束时 `end_title`/`end_subtitle` 为 `null` → 不显示结算层（沿用现有 `game_over` 门控）。

🔴 **验收断言（给 QA 用）**：QA **只对 `/api/state` 的 `end_title`/`end_subtitle` 断言**（前端已无映射，不测前端字符串拼接）；任何 `end_reason != "unification"` 时，这两个字段**不得含「统一」「一统天下」**。

### 3.5 后端事件文案（第三处硬编码「统一」）

`api/game_manager.py:791`（`advance_turn` 内，对局结束时）当前恒发：

```python

    if self.engine.winner:
        w = FACTIONS.get(self.engine.winner, self.engine.winner)
        self._add_event(f"🏆 {w} 一统天下！", "victory")   # 🔴 不分「城市最多」与「真统一」
    else:
        self._add_event("游戏结束：平局", "victory")
```

→ 改为调用**唯一文案真源** `format_end_copy(...)`（与 `/api/state` 同源，见 §3.6）：

```python

title, _subtitle = format_end_copy(
    self.engine.end_reason, self.engine.winner,
    self.engine.turn, self.engine.max_turns, self.config.stalemate_turns,
)

```

🔴 **文案单一真源（已定 ①）**：**语义真源 = 引擎 `end_reason`；文案真源 = 后端 `format_end_copy`**。后端事件与 `/api/state` 的 `end_title`/`end_subtitle` 同调此函数，前端 verbatim 渲染 —— 全局只有 1 份文案映射，根治三处漂移。

### 3.6 文案单一真源的落地方案（接口决策，待主理人定）

QA 提的「同句文案存在两个真源 = 下一个 H1」成立。两条候选，**推荐方案 ①**：

| 方案 | 真源位置 | 做法 | 优点 | 缺点 |
|------|---------|------|------|------|
| **① 后端 canonical（推荐）** | **Python 后端单一函数** | 后端 `format_end_copy(end_reason, winner, turn, max_turns, stalemate_turns) -> (title, subtitle)`；后端事件（§3.5）与 `/api/state` 的 `end_title`/`end_subtitle` **都用它**；前端 Overlay **verbatim 渲染**，不做映射 | 只有 1 份映射（Python），QA 只测一处 | 前端失去文案自由度；接口需新增 `end_title`/`end_subtitle` 字段 |
| ② 前端 canonical | 前端 `end_reason → 文案` 映射 | 后端只发 `end_reason`；后端事件也读 `end_reason` 自行映射 | 文案可随前端热更新 | Python/TS 各一份映射 = 仍是两个真源，未根治 |

> ✅ **已定：方案 ①（主理人拍板）**。`end_reason` = 语义真源；后端 `format_end_copy(...)` = 文案真源；后端事件与 `/api/state` 的 `end_title`/`end_subtitle` 同调此函数；前端 verbatim 渲染、TS 内不得再写映射。方案 ②（前端 canonical，Python/TS 双映射）**不采纳**。
> 建议签名：`format_end_copy(end_reason, winner, turn, max_turns, stalemate_turns) -> (title, subtitle)`；`title` 含图标（unification 🏆 / timeout ⏳ / stalemate ⚖️ / 平局 🤝），`subtitle` 为次要说明行。

🔴 **红线（QA 新证据 S3 触发）**：**标题与副行必须出自 `format_end_copy` 同一函数、同一 `end_reason`（+ winner）输入**，**禁止只替换标题那处**。改动前 `GameOverOverlay.tsx:32` 的 `reason` 只有 2 个取值（`回合耗尽`/`一统天下`），导致**平局时副行仍写「一统天下」**（QA S3 实锤）。本方案下平局（`winner==null`）→ title 与 subtitle **同时**走 §1.1 的「未分胜负」分支，**两行都不含「一统」**。
