### 🔴 可复现性事故与修复（重要，影响所有数字可信度）

首次跑完主实验后自查发现：**同一 seed 在不同进程得到不同结果**
（exp6 两次复跑：271 次 vs 245 次出征）。

**根因**：引擎内部存在依赖 `set`/`dict` 迭代顺序的逻辑
（`GameEngine._spread_influence` 用 `assigned: set` +遍历 `self.cities.values()`
决定影响力扩散方向），而 Python 字符串哈希**默认按进程随机化**
（`PYTHONHASHSEED=random`）→ 迭代顺序逐进程变化 → 随机数消耗序列变化 → 结果漂移。
`sim_lib.stable_hash` 只稳定了玩家种子，**没有稳定引擎内部的集合遍历**。

**修复**：`pacing_lib.ensure_reproducible()` 在每个实验脚本入口强制
`PYTHONHASHSEED=0`（必要时 `os.execv` 重启）。修复后三次独立进程复跑
**逐位一致**（263/41、263/41、263/41）。
**本文所有数字均在修复后重跑。**

> ⚠️ 附带发现：其他 agent 在实验期间依据本报告的 P0 建议并发实施了修复
> （`game/tile.py`、`game/constants.py`、`players/cli_player.py`），
> 并已提交为 `150fa87`。这导致"跑 base"不再等于"修复前"。
> 为此新增 `P.use_pristine_baseline()` 与 `exp10`，把修复前/后

> 且在 P0 已提交后仍能正确重建修复前状态（实测：当前 HEAD base=0 对，
> 锁定基线后=114 对 ✅）。

## 4. 🔴 真正的根因链

### 堵点 1：PEAK 地形切断 24.5% 的地图（实验 0b/0c/4）

`exp0c` 排除寻路算法问题（A* 与 BFS **0 处不一致**），定位到
`Tile.is_passable()` 硬编码不可通行集合含 `PEAK`。
`exp4` 用运行时补丁精确隔离元凶：

| 变体 | 不可达城对 | 被切断势力 | 孤立中立城 |
|---|---|---|---|
| **base** | **114 (24.5%)** | **liubei, liuyan** | **beihai, linzi** |
| water（仅水域可通行） | 114 (24.5%) | 同上 | 同上 |
| nomountain（仅山脉可通行） | 59 (12.7%) | 无 | beihai, linzi |
| **nopeak（仅山峰可通行）** | **0 (0.0%)** ✅ | **无** | **无** |
| all（全地形） | 0 (0.0%) | 无 | 无 |

**`PEAK`（587 格）是唯一元凶。** 让山峰可通行即 100% 连通，
且**保留山脉（364 格）作为天然屏障**——不影响战略纵深，纯粹修复连通性。

> 注：全图 24000格中 **70.7% 是 deep_water**，可通行仅 25.3%。
> 地图本身是群岛形状（base 下 22 个连通分量，主大陆 5994 格），
> 这是地图生成器的既有设计；PEAK 叠加在水域之上，把大陆切成了互不相连的碎块。

### 堵点 2：94% 的进攻命令被引擎直接拒绝（实验 6/10）⭐ 最大单一原因

**权威口径 = `exp10` 的 `before` 组**（同时还原 PEAK 阻断 + 将领跨城兜底，5 局/组，
配对 seeds，96 回合）：

| 指标 | 数值 |
|---|---|
| 出征命令总数 | 3392 |
| **成功率** | **185/3392 = 5.5%** 🔴 |
| `general_not_in_city` 占失败 | **2465/3207 = 76.9%** |
| `no_hex_path` 占失败 | 742/3207 = 23.1% |

**根因在 `players/cli_player.py`**：出发城没有本地将领时，代码跨城兜底取
"己方第一个将领"，而那个将领在**别的城** → 被 `engine.py:508`
`if general.location != from_city.id` 拒掉。

数据佐证：12 将领分散在每方 2 座城（如 caocao：`xuchang` 5 / `chenliu` 3），
从 A 城出兵时兜底常取到 B 城将领 → 必然被拒。

> ⚠️ **口径说明（已修正）**：`exp6 --baseline` 早期版本只还原**地形**，
> 未还原 `cli_player` 的跨城兜底，测得的"92.7% / 成功率 16.7%"是
> 「地形阻断 + 将领半修」的混合态，**不等于真正的修复前**。
> 现已修正为**完整还原 P0**（地形 + 将领兜底），重测得
> 成功率 **12.5%**、`general_not_in_city` 占失败 **76.8%**，
> 与 `exp10 before`（96 回合）的 **5.5% / 76.9%** 口径一致 ✅
> （绝对值差异来自动/回合数不同：40 vs 96 回合，回合越多失败累积越多）。
> **报告结论一律以 `exp10` 为准。**

### 堵点 3：CLIPlayer 进攻信心门槛（实验 8）— 唯一能让战斗翻倍的杠杆

在"PEAK 可通行 + 将领归属已修"前提下，逐项放开决策层约束（4 局/组，48 回合）：

| 变体 | 参数 (cap, agg, 敌城门槛) | 战斗/局 | 相对 base | 存活势力 |
|---|---|---|---|---|
| **base** | (8, 1.3, **1.0**) | 31 | — | 12 |
| cap16 | (**16**, 1.3, 1.0) | 31 | 0% ⚪ | 12 |
| agg2 | (8, **2.5**, 1.0) | 32 | +3% ⚪ | 12 |
| **weak** | (8, 1.3, **0.6**) | **62** | **+100%** 🔴 | 11 |
| all | (16, 2.5, 0.6) | 56 | +81% 🔴 | 10 |

**判读**：
- 命令数上限（8→16）与出手概率（1.3→2.5）**几乎无效**（0% / +3%）。
- **唯一有效的是放宽"兵力需 ≥ 守军"**（`cli_player.py:152`）。
  这解释了为什么"战斗少"：CLIPlayer 只在**兵力绝对优势**时才敢打，
  大量本可打赢的战役根本没发起。
- **即使战斗翻倍，12 方依然几乎全部存活。**

### 堵点 4：城市实际打不下来（实验 9 + 机制追踪）

**(a) 军事发展让城墙"越修越硬"** — `city_system.py:140-148`

```python
elif develop_type == "military":
    wall_increase = MILITARY_WALL_REPAIR          # 200
    city.wall_hp = min(city.wall_hp + wall_increase, city.wall_max_hp + wall_increase)
    city.wall_max_hp += wall_increase             # ← ⚠️ 上限永久抬高，永不回落
```

"发展军事"不是修墙，而是**每回合永久抬高城墙上限 200 点**。
实测许昌 40 回合内 `wall_max_hp` 3200 → 7400（**+131%**），
而每回合攻城伤害只有 400。40 回合内发展命令分布：
economy 309 / **military 281** / culture 133——军事发展占 39%
（CLIPlayer 对 `aggression > 0.6` 的势力固定选"military"）。

`exp9` 对照（4 局/组，96 回合）：

| 变体 | 战斗/局 | 存活势力 | 城墙完好率 | 统一局数 |
|---|---|---|---|---|
| base（上限永久+200） | 60 | 12 | 0.613 | **0** |
| cap（上限不增长） | 61 | 12 | 0.704 | **0** |
| hard（不涨+伤害×2） | 58 | 12 | 0.689 | **0** |

**该修复无效**（60→61，存活仍 12），瓶颈在下一层。

**(b) 围城兵力交换比是攻方吃亏**（引擎埋点，40 回合 28 场战斗）

| 指标 | 数值 |
|---|---|
| 攻方平均伤亡 / 初始兵力 | **63.2%** |
| 守方平均伤亡 / 初始兵力 | **77.4%** |

单次围城攻方损失 63% 兵力却**打不下城**（`battle_type` 全为 `siege`，
无一取胜）。攻方兵力逐次递减，而守军每回合可补至`level × 1000` 上限
→ **进攻方永远打不穿消耗战**。

## 7. 推荐参数

### 7.1 关于「`ARMY_MARCH_SPEED = ?` × `max_turns = ?`」

**诚实结论：这两个参数都不是有效杠杆，无法达成"战斗变多且不碾压"。**
若发布必须给值，基于实测的**低风险**选择：

| 参数 | 推荐 | 理由 |
|---|---|---|
| `ARMY_MARCH_SPEED` | **保持 4** | 调到 6/8/10 实测无收益（战斗反降 3%），却让 LLM reasoning 的
估算误差放大 2.5 倍（LLM 按"整支军队每回合移动"理解，引擎实为按地形 cost 逐格推进）。 |
| `max_turns` | **48**（从 192 下调） | 战斗密度 0.479 → **0.932**（+95%），节奏提升近 1 倍；
统一度无变化（无副作用）。48 回合 = 12 年（每回合 1 季度）。 |

**这两项都只是"缓解"，不解决"12 方永远打不完"。**

### 7.3 ⚠️ 碾压风险（用户明确要求指出）

**当前设计下"碾压"无法通过行军速度调节**——因为 12 方势力在 192 回合内
**没有任何一方能被灭**（存活 12/12，最大占比 0.16~0.21，HHI≈0.10，
距理论下限 1/12=0.083 很近）。所谓"胜者"是城市数最多者，非征服者。

因此 **"战斗变多"与"不碾压"当前无法同时实现**——因为根本没有"一方碾压"发生。
若P2 修好后战斗能真正攻下城池，**必须重跑碾压检测**
（`run_simulation.py` 的 OP 嫌疑阈值 2× 公平份额 = 16.67%）。

**已观察到的偏斜**（P0 修复后仍存在，需 P1/P2 后复核）：
`sunjian` / `caocao` / `yuanshu` / `zhangjiao` 占据胜率前列，
`han` / `dongzhuo` / `gongsunzan` 常年 0 胜。
PEAK 修复已使 `liubei` / `liuyan` 不再被孤立（其 0 胜另有原因，
需 P1/P2 阶段单独归因）。
