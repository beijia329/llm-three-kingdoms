## 0. 一页速览

### 0.1 五个缺口的性质分类

| # | 缺口 | 本质是 | 影响面 | 改动性质 |
|---|------|--------|--------|----------|
| 1 | 智力在外交侧不可达 | **接线缺失**（数据在，出口没通） | 一个属性、一条设计承诺 | 命令参数 + Prompt，低 |
| 2 | 「围城」名不副实 | **概念未实现**（只有瞬时战斗，没有跨回合围城状态机） | 战争节奏、战争多样性 | 需新增回合钩子 + 状态机，中高 |
| 3 | 战斗在界面上不可见 | **只读侧缺失**（战果已算出，没送到观众眼前） | 本项目定位（围观台）的核心 | 事件总线 + 序列化 + 渲染，低到中 |
| 4 | 经济无出口（资源堆积） | **sink 缺失 + 数值天花板** | 长期决策质量、模型分差 | 数据 + 新命令/新机制，中 |
| 5 | 势力开局不均衡 | **有待裁决的取舍**（特性 vs 缺陷） | 评测公平性 | 数据（可选）+ 判定口径，低 |

### 0.2 优先级建议（我的排序与理由）

| 序 | 缺口 | 为什么排这个位 |
|---|------|----------------|
| **1** | **缺口 3 战斗可视化** | 成本最低（战果数据已算好，只缺传输与呈现）、零平衡风险、**直接打在项目定位上**（「看/玩割裂」是围观台的致命伤）。设计工作重（「看什么」要先定义），工程工作轻。是**回报/cost 比最高**的一项。 |
| **2** | **缺口 1 智力可达性** | 改动最小（Prompt 一行 + 参数回填），却**恢复了一条已写入 Prompt、已写入常数、却从未生效的设计线索**（谋士在战场上/外交上无用）。属于「性价比极高的补洞」。 |
| **3** | **缺口 4 经济出口** | 解冻长期决策：当钱粮不再是约束，模型的中后期策略退化为「无脑堆兵」。它**决定了评测能不能区分「会经营的模型」与「不会的模型」**。需先定 sink 形态再改。 |
| **4** | **缺口 2 真·围城** | 价值高（让战争从「一次判定」变成「多回合博弈」，制造 tension curve），但**需要新的架构钩子**（见 §6），且动战力平衡，回滚成本最高。建议排在钩子落地之后。 |
| **5** | **缺口 5 开局均衡** | 严格说不是「玩法缺口」，是**决策项**。见 §5 表态：我判断为**特性为主、缺陷为辅**，处理方式是「补翻盘手段 + 声明评测口径」，而非抹平开局。 |

### 0.3 一句话结论

**缺口 1、3 是接线问题，缺口 4 是数值/机制缺件，缺口 2 是架构能力缺件，缺口 5 是口径问题。** 前两者应立刻做；后三者需要主理人先拍板范围与钩子形态。

### 1.2 流言命令的完整调用链（实读）

```
LLM 输出 rumor 命令
  → players/llm/output_parser.py:369  rumor 必填参数仅 ["city"]（spy_general 不在必填）
  → players/llm/llm_player.py:80      PARAM_MAPPING 里有 spy_general（映射存在）
  → players/llm/prompt_builder.py:195 「9. rumor - 散布流言 / 参数：city, target_general(可选)」
                                       ★ 命令说明里【没有】spy_general
  → game/engine.py:719 _execute_rumor
       :725  spy_intelligence = 50            ← 默认值
       :726  if cmd.spy_general:              ← 仅当传了才覆盖
       :733  target_faction=""  ← 注释「由 GameEngine 查」，实际无人回填
  → game/systems/diplomacy_system.py:167 spread_rumor(...)
       :193  用 spy_intelligence 算成功率
       （target_faction 形参在整个函数体内未被使用）
```

**结论**：智力影响流言的链路**代码上通、生产上不通**。三个独立的断点：
1. **Prompt 不告诉 LLM 有 `spy_general` 这个参数**（`prompt_builder.py:195`）→ LLM 不会填 → 恒取默认 50。
2. 即便 LLM 填了，`target_faction` 恒为空串且**在 `spread_rumor` 内根本没被读**（`diplomacy_system.py:167-219`）→ 说明该参数是历史遗留，不是「待回填」。
3. `output_parser.py:369` 不校验 `spy_general` 合法性（未核实是否有后续类型校验）。

### 1.3 「围城」当前的真实行为（实跑探针结论）

探针 `/tmp/probe_siege.py`（seed=1，60 回合）：**在所有回合边界观测 `city.is_besieged`，累计出现 0 次**；同期发生 **86 场战斗**。

| 断言 | 位置 | 核实结果 |
|------|------|----------|
| 军队抵达敌城即置 `is_besieged=True` | `game/battle/army_movement.py:364` | ✅ 存在 |
| 战斗结算末尾清 `is_besieged=False` | `game/engine.py:1081`（`_apply_battle_result`） | ✅ 存在 |
| `is_besieged` 影响民心（-3/回合） | `game/systems/city_system.py:376`（在 `_calculate_morale_change` 内） | ⚠️ 该函数只被 `update_city` 调用（`city_system.py:314`），而 hex 模式走 `calculate_resources`（`engine.py:855`），**`update_city` 仅在非 hex 分支执行**（`engine.py:868`）→ hex 下**永不执行** |
| 围城对城墙造成伤害 | `battle_resolver.py:191` `_process_siege_round` → `:289` `calculate_wall_damage` | ✅ **战斗内的围城回合确实在扣城墙**（探针：73 场攻击战中 28 场起始城墙>0 且被扣减） |
| 跨回合围城可累积 | `battle_resolver.py:152-154` 回写 `ctx.wall_hp` | ✅ 城墙耐久跨战斗持久（`engine.py` 回写 `defender_city.wall_hp`） |

**精确结论**：**「围城」不是一个跨回合的持续状态，而是一场发生在单个 `process_turn` 内的瞬时战斗。** `is_besieged` 标志在「到达」和「战斗结算」之间被设置、在同一次 `process_turn` 内被清除，**任何回合边界的外部观察者（LLM、前端、回放）都看不到它**。民心 -3 的围城惩罚是 hex 模式下的死代码。

对照 `docs/design/battle-system.md:131`「每回合对城墙造成伤害」——**文档描述的是「战斗回合」粒度的城墙伤害（一个 process_turn 内最多 10 个战斗回合，`MAX_BATTLE_ROUNDS`），不是「游戏回合」粒度**。文档口径与实际实现存在语义错位。

### 1.4 战斗数据的可用性（供缺口 3）

战斗结算时，下列字段**全部已在内存中算出**（`game/models.py:449` `BattleContext`、`:534` `BattleResult`）：

| 观众需要的 | 引擎是否已有 | 字段 |
|-----------|--------------|------|
| 交战方 | ✅ | `ctx.attacker_faction` / `ctx.defender_faction` |
| 兵力对比 | ✅ | `ctx.attacker_total_soldiers` / `ctx.defender_total_soldiers` |
| 伤亡 | ✅ | `result.attacker_casualties` / `result.defender_casualties` |
| 结果 | ✅ | `result.result`（Enum） |
| 攻下哪座城 | ✅ | `result.captured_city` |
| 城墙受损 | ✅ | `ctx.wall_hp` / `ctx.wall_max_hp` |
| **进攻方向（从哪打哪）** | ⚠️ 可推导 | 军队 `Army.from_city` / `to_city` / `current_hex` + 城市 `position`（`models.py:190` / `:108`）——**存在但未被打包进战果** |
| **谁指挥** | ⚠️ 可推导 | 军队 `general_id` → `General.name` |

**结论**：缺口 3 的瓶颈**不在引擎，在传输与呈现**。战果算完即被 `_apply_battle_result` 消费并丢弃，只有一个聚合计数 `battles_fought` 活着走出 `process_turn`（`engine.py:952`）。前端唯一能拿到的战斗信息是文字事件的「第 N 回合 X 场战斗」（`api/game_manager.py:663`）。

### 1.5 经济（资源堆积）实跑证据

探针 `/tmp/probe_econ.py`（seed=1，40 回合），九方存活势力库存：

```
faction    cities     gold     food  garrison    cap(守军上限)
han             2   115780   192948      6156   7000
liuyan          3   124863   157239      8300   9000
yuanshao        6   108620   137609     10368  14000
caocao          4    75686   128108     10000  10000
```

金/粮在 40 回合内堆积到 **6–12 万 / 7–19 万**量级，而**主口粮 sink（征兵）被守军上限锁死**（`city_system.py:225-232`，上限 = `level × GARRISON_CAP_PER_LEVEL(1000)`，`city_system.py:281`）。当前金的其它 sink：

| sink | 位置 | 为什么吸不动 |
|------|------|--------------|
| 征兵 | `city_system.py:207` `recruit` | 受守军上限约束 → 满员即失败 |
| 发展 | `city_system.py:107` `develop`，成本 `200 + level×100`（`city_system.py:201`） | 军事发展只修墙（不抬上限，`city_system.py:157`）；经济是线性 +20（`ECONOMY_GOLD_BONUS`）；文化 +5 民心。三者都**无高值出口**，且可无限重复直到收益为 0 |
| 赏赐 | `general_system.py:188` `reward`，100 金 ≈ +5 忠诚（`REWARD_LOYALTY_BONUS_PER_100_GOLD=5`），上限 100（`MAX_LOYALTY_FROM_REWARD=100`） | 忠诚向 baseline 回归（`LOYALTY_REGRESSION_PER_TURN=1`，`general_system.py:235`）→ **赏赐会被回合衰减吃掉**，长期是无效 sink |

**结论**：这是一个**价值天花板问题**（value ceiling）。钱的边际效用在中后期趋零，因为没有「把资源转化为战略优势」的高值出口。

## 2. 缺口 1：智力在外交侧不可达

### 2.1 机制定义

**目标**：让「智力」这条已存在的设计线（`models.py:266` 描述即「智力 影响计谋」）真正参与外交/谍报博弈，恢复「谋士 vs 谋士」的对抗维度。

**方案（三选一，我推荐 A）**：

- **方案 A（推荐）：把 `spy_general` 补进 Prompt + 回填 target。**
  - LLM 侧：在 `prompt_builder.py:195` 的 rumor 说明里加上 `spy_general (执行间谍的将领，智力越高成功率越高；不填则按智力 50 计)`。
  - 引擎侧：`_execute_rumor`（`engine.py:719`）**在未传 spy_general 时，自动选取本势力智力最高的空闲将领**作为执行者，而不是恒取 50。这样智力自然进入公式。
  - `target_faction`（`engine.py:733`）：要么删掉这个死参数，要么真的用 city 反查归属。**我倾向删除**——`spread_rumor` 函数体从不读它（`diplomacy_system.py:167-219`），保留只会误导后续读者。

- **方案 B：把「计谋」提升为独立子系统。** 引入 `INTELLIGENCE_STRATEGY_SUCCESS_RATE`（`constants.py:445`）真正接线，做「离间/伪报/策反」三类计谋。成本中，但它其实属于「新玩法」，不属于「补洞」。

- **方案 C：不动。** 承认流言只是一条低重要度命令，智力主要靠攻城器械出口。

### 2.2 可感知反馈（围观台视角）

- **观众看得到**：战报/事件流出现「【流言】曹操之谋士荀彧（智力 92）蛊惑张辽，忠诚 -5」这类**带人名与智力值的句子**；被离间的将领在武将榜上忠诚条变色（前端已有忠诚展示，`web/src/types.ts:53`）。
- **反面**：当前观众看到的是「流言失败」这种无主语、无信息量的文字（`diplomacy_system.py:218`）。**机制不可见 = 不存在**（本项目铁律）。

### 2.3 与现有系统的接口

| 依赖 | 位置 |
|------|------|
| 命令定义 | `game/models.py:366` `RumorCommand.spy_general` |
| 处理器 | `game/engine.py:719` `_execute_rumor` |
| 成功率公式 | `game/systems/diplomacy_system.py:191-195` |
| 常数 | `constants.py:469-476`（`RUMOR_*`） |
| 命令注册 | `game/command_registry.py`（`rumor` 已注册） |
| Prompt | `players/llm/prompt_builder.py:195` |
| 参数映射 | `players/llm/llm_player.py:80` |

### 2.4 可插拔性评估 🔴

**这个系统天然可插拔，且不需要新钩子。** 它完全落在**已有的命令扩展点**（`command_registry.py`）内：改一个处理器的行为 + 一条 Prompt。

- 挂载钩子：**Command Registry**（`command_registry.py:36` `register_command`）。
- 唯一需要注意：如果走方案 A，`_execute_rumor` 是引擎方法，属于「改引擎核心」——但改的是**一个处理器的内部实现**，不是分发逻辑（分发已抽到注册表）。符合「加玩法不改引擎核心」的目标。
- 若要彻底 mod 化，可把 rumor 处理器抽成独立模块 `game/systems/espionage_system.py`，由注册表挂载。

### 2.5 代价与风险

| 项 | 评估 |
|----|------|
| 改动量级 | 极小。Prompt 1 行 + 处理器 ~15 行 + 删 1 个死参数 |
| 是否动战力平衡 | **不动**。流言只影响忠诚度，不直接改伤害/产出 |
| 回滚成本 | 极低（单函数，无状态迁移） |
| 风险 | 若「自动选智力最高将领」会让高智势力过强 → 可用「需该将领空闲/在城内」约束。数值上每点智力仅 +0.5% 成功率（`RUMOR_INTELLIGENCE_FACTOR`），天花板已被 `min(0.9)` 限制（`diplomacy_system.py:195`） |

### 2.6 优先级建议

**第 2 位。** 成本最低、恢复一条已承诺的设计线，且不触碰平衡。适合作为「打样」验证「加玩法 = 小改动」这一可插拔目标是否成立。

## 3. 缺口 2：「围城」名不副实

### 3.1 机制定义

**现状**：没有跨回合围城。军队到达敌城 → 同回合内跑完战斗 → 状态清零。战争是「一次性判定」。

**目标**：让「围城」成为一个**持续多回合的状态机**，让攻城从「掷一次骰子」变成「converging pressure（逐步加压）」的过程，产生 tension curve。

**建议机制**：

1. **围城状态持续**：军队抵达敌城后进入 `BESIEGING`，**不再立即结算总攻**，而是每回合执行一次「围城结算」：
   - 城墙按公式持续受损（复用 `calculate_wall_damage`，`battle_resolver.py:289`）；
   - 城内守军受到断粮/民心压力（把死掉的 `_calculate_morale_change` 里的围城分支，`city_system.py:376`，接到 hex 路径）；
   - 攻城方每回合承受粮草消耗（`ARMY_FOOD_COST_PER_SOLDIER=0.15`，已在 `army_movement.py` 计）。
2. **剧本化结局**：城墙破、守军士气崩、或攻方断粮 → 触发总攻判定（进入现有 `resolve_battle`）。
3. **可选**：守军可出击（打破围城），使围城成为双向博弈。

### 3.2 可感知反馈

- 观众能在地图上**持续看到一座被围的城**：攻城塔徽记、脉冲、城墙耐久条逐回合下降、守军数字逐回合减少（这些视觉组件**已存在**：`CityMarker.tsx:114` 围城徽记、`:93` 脉冲、城墙/守军数据已有）。
- 事件流出现「【围城】曹操围困许昌（城墙 2400→2000）」，形成**连续叙事**而非一次性弹窗。
- **关键**：当前这些视觉组件因 `is_besieged` 在回合边界永远为 false（§1.3）而**几乎从不显示**——围城一旦变成持续状态，视觉资产立即被激活。

### 3.3 与现有系统的接口

| 依赖 | 位置 | 说明 |
|------|------|------|
| 围城标志 | `models.py:147` `City.is_besieged` / `:148` `besieging_armies` | 字段已存在 |
| 置位点 | `army_movement.py:364-366` | 已存在 |
| 清零点 | `engine.py:1081-1082` | 需改（改为「城墙未破则保留」） |
| 城墙伤害 | `battle_resolver.py:191,289` | 复用 |
| 民心围城惩罚 | `city_system.py:376` | **当前死代码**，需接到 hex 路径 |
| 战斗调度 | `battle_scheduler.py:59` `detect_battles` | 需改为「仅在满足总攻条件时才结算」 |
| 探查守卫 | `engine.py` `_process_hex_movement` | 已存在 |

### 3.4 可插拔性评估 🔴

**这是五个缺口里唯一需要「新架构钩子」的。**

- 现状：`process_turn`（`engine.py:799`）是一条**硬编码固定序列**（资源→行军→扫荡→人设→忠诚→战斗→清理→胜负→建国→回合递增），**没有任何「回合相位钩子」**可供子系统注册。
- 已有的唯一扩展点是 **命令注册表**（`command_registry.py`）——但它只管「命令执行时」，管不了「每回合结算时」。
- **建议新增：回合相位钩子（Turn-Phase Hook Registry）**，形态与命令注册表对称：

```
# game/turn_phases.py（建议）
PHASES = ["turn_start", "resource", "movement", "combat", "turn_end"]
register_phase_handler(phase, handler, order=100)   # handler(engine) -> None
```

  然后把 `process_turn` 的固定序列**重构为按相位遍历注册表**，内置系统作为默认注册项。这样：
  - 围城系统 → 注册到 `turn_end`（或 `combat` 之后）；
  - 经济 upkeep → 注册到 `resource`；
  - 未来任何 DLC → 注册一个相位处理器即可，**不改 `process_turn`**。

- **这是「钢铁雄心式逐步更新」缺的那根总钩子。** 建议把它作为独立基础任务（工程岗）先行落地，之后再上围城。

### 3.5 代价与风险

| 项 | 评估 |
|----|------|
| 改动量级 | 中高。状态机 + 相位钩子 + 战斗调度改造 |
| 是否动战力平衡 | **会**。围城持续化会显著改变攻城成功率与战争节奏；需单独立项做 `tests/balance/` 实验（参考 exp11/exp16 的方法论） |
| 回滚成本 | 中（新增状态字段 + 钩子，可加 feature flag 关闭） |
| 风险 | ① 与 exp15/16 已证的「打不完」问题叠加，可能加剧雪球或冻结（**必须先跑平衡实验**）；② 相位钩子重构 `process_turn` 有回归风险（`process_turn` 是确定性关键路径，参考 ADR-0002） |
| 前置依赖 | **回合相位钩子**（§6）必须先落地 |

### 3.6 优先级建议

**第 4 位。** 价值高，但依赖新钩子、动平衡、改动大。**先落地钩子（§6），再单独立项围城 + 平衡实验。**

## 4. 缺口 3：战斗在界面上不可见

### 4.1 机制定义

**不是新增玩法，是补齐「只读侧」。** 引擎已经算出完整战果（§1.4），但没有广播、没有序列化、没有呈现。

**方案三步**：

1. **广播**：在 `_apply_battle_result` 内发布 `BattleEndedEvent`（`event_bus.py:89`，已定义未发布）与 `CityCapturedEvent`（`event_bus.py:43`）。⚠️ 另一路 agent 正在做这件事（工作区 diff 已见 `TurnStartedEvent/BattleEndedEvent/TurnEndedEvent` 的 publish），**本文不重复派单，只补充字段需求**。
2. **序列化**：在 `api/game_manager.py:277` `get_state` 增加一个 `recent_battles` 列表（近 N 场），字段见 §4.3。
3. **呈现**：前端在地图上画进攻箭头/交战点；战报事件与地图联动。

### 4.2 观众要看到什么（这是「设计问题」，需精确定义）

> art-director 负责「怎么画」，本节负责定义「画什么」。**验收标准：单场战斗，观众只看地图、不看文字，3 秒内能复述三件事。**

**三件事（按优先级）**：

1. **谁在打谁** —— 进攻方势力 → 防守方势力（用双方势力色 + 旗号）。
2. **打的什么结果** —— 城被攻下 / 守住了 / 攻方溃退（三种状态的视觉区分：占领=旗帜更换动画；守住=守军数字回升；溃退=撤退抖动，`ArmyMarker.tsx:73` 已有 `retreat-shake`）。
3. **从哪来、打向哪** —— 一条**进攻箭头**，起点 = 攻方出发城，终点 = 目标城；箭头粗细/颜色反映兵力比。

**三件事之外（加分项，非必须）**：兵力对比数字（如「3200 ⚔ 1500」）、城墙破损、主将名。

**呈现窗口**：一场战斗在**一个回合内**结算完毕（§1.3），所以战斗动画本质是**回放**而非实时。建议：回合推进后，对最近 N 场战斗做**逐场短回放**（每场 1–2 秒），而非简单闪烁。

### 4.3 需要哪些数据、引擎现在有没有

| 数据 | 引擎现状 | 位置 |
|------|----------|------|
| 攻方势力 / 守方势力 | ✅ 已有 | `ctx.attacker_faction` / `defender_faction`（`models.py:460`） |

**结论**：**没有一项需要新增游戏逻辑**。缺的只是「在 `_apply_battle_result` 里把上述字段打包成一个 DTO，通过事件 + 状态快照送出去」。方向坐标需要一次 `cities.get(from_city).position` 查询。

**建议的 `BattleReport` DTO 字段**：

## 5. 缺口 4：经济无出口（资源堆积）

### 5.1 机制定义

**问题**：金/粮在中后期无高值出口（§1.5），长期决策退化为「堆兵」。这是 **value ceiling**，不是「数值太高」。

**方案（分层，建议组合 1+2）**：

1. **接活已有的低效 sink（成本最低）**
   - **发展改为递减/非线性**或增加新的发展维度，让钱能持续换取优势；
   - **赏赐对抗忠诚回归**：当前赏赐的忠诚会被 `LOYALTY_REGRESSION_PER_TURN` 吃掉（`general_system.py:235`）→ 可让「重赏」产生**永久忠诚基准提升**（抬高 `loyalty_baseline`），使赏赐有长期价值。
2. **新增高值出口（中等成本，需新命令）**
   - **城墙/工事升级**（当前 `develop military` 只修墙不抬上限，`city_system.py:157`——可引入**有限次**的城防等级提升）；
   - **征兵上限随人口/发展提升**（当前硬锁 `level×1000`，`city_system.py:281`）——让「经营」能突破军事天花板；
   - **粮草→士气/募兵加成**（把粮草变成战斗资源）。
3. **降低产出（备选）**：直接下调产出系数——但这只是延缓堆积，不解决「没有高值出口」的结构问题，**不推荐单用**。

### 5.2 可感知反馈

- 观众在数据面板能看到**资源曲线不再单调上升**（前端 `web/src/components/Panel.tsx` 的 DataPanel 已有城池统计）。
- 更关键：**模型的决策理由（reasoning）会体现经营策略**（前端已有「决策」面板，`game_manager.py:598`）。当钱能换东西，模型会开始算经营账，评测才能区分「会经营」与「不会经营」的模型。

### 5.3 与现有系统的接口

| 依赖 | 位置 |
|------|------|
| 资源产出 | `game/systems/resource_system.py:307` `calculate_resources` |
| 征兵 | `game/systems/city_system.py:207` `recruit`、`:281` `_get_max_garrison` |
| 发展 | `game/systems/city_system.py:107` `develop` |
| 赏赐 | `game/systems/general_system.py:188` `reward` |
| 守军上限常数 | `GARRISON_CAP_PER_LEVEL=1000`（`city_system.py:89`） |
| 忠诚回归 | `LOYALTY_REGRESSION_PER_TURN=1`、`DEFAULT_LOYALTY_BASELINE=70`（`constants.py:331,338`） |
| 命令注册 | `game/command_registry.py`（新 sink 可注册新命令） |

### 5.4 可插拔性评估 🔴

**部分可插拔。**

- **已有命令的调整**（赏赐/发展/征兵）：落在命令处理器内，属**命令扩展点**，可插拔。
- **新增入口**（如「城墙升级」「募兵加成」）：可注册**新命令**（`command_registry.py`），**不改引擎核心**——完全符合 mod 化目标。
- **若要做「每回合维护费/通胀」类被动 sink**：需要**回合相位钩子**（§6），注册到 `resource` 相位。
- 结论：**大部分可挂命令注册表；被动型 sink 需回合钩子。**

### 5.5 代价与风险

| 项 | 评估 |
|----|------|
| 改动量级 | 中。数值 + 若干命令；若含被动 sink 则 + 钩子 |
| 是否动战力平衡 | **会**（尤其动守军上限/产出）。需平衡实验 |
| 回滚成本 | 中（数值可回退；新机制可加 flag） |
| 风险 | ① 破坏现有 pacing（exp15/16 的结论对数值敏感）；② 与缺口 2 叠加时的影响未测；③ 可能引入新的 dominant strategy（例如「堆经济→无敌」）——需专门检查 |

### 5.6 优先级建议

**第 3 位。** 它决定「长期博弈是否成立」，但需要先定 sink 形态再动手。建议先做 §5.1 第 1 层（低成本、复用现有 sink），跑一轮平衡实验后再决定是否上新命令。

## 6. 缺口 5：势力开局不均衡（特性 vs 缺陷）

### 6.1 我的表态

**结论：这主要是「特性」，但当前缺一块「让弱方有翻盘手段」的补丁；不建议抹平开局。**

理由（分三层）：

1. **从题材看，它是特性。** 三国 184 年本就是极不均势：汉室据两京、曹操多谋士、董卓孤悬天水。项目 `concept.md:48` 的设计支柱之一是「地理即棋盘」——地图不对称正是战略博弈的来源。抹平它等于放弃「远交近攻」的天然成立。
2. **从评测看，它是缺陷——但缺陷在「口径」，不在「数据」。** 项目定位是「公平比试大模型」（`concept.md:22`）。**2.75× 的兵力差 + 4× 的将差会让「谁赢」被开局决定，掩盖模型差异。** 但正确解法不是改数据让每个势力一样强，而是**声明并锁定评测口径**：同一 seed 下每个模型跑同一势力（或轮流坐庄），比较「同起点下的相对表现」，而非「绝对胜负」。
3. **从观赏看，它需要翻盘手段。** 围观台的戏剧性来自 tension curve（此消彼长），而非「开局即定」。当前 `v4-conquest-pressure.md` §4.5.2 已实测：**雪球源是杠杆 A，不是 G**；撤回 A 后翻盘率 3/5——**说明翻盘机制在现有系统里是稀缺的**。

**所以我的处理建议**：

- **保留开局不均衡**（不动 `data/cities.json` 的守军/将领分布）。
- **补「弱方翻盘手段」**（这是真正该做的「玩法补洞」）：
  - 方向 1：**弱势补偿（catch-up）**——当某势力城数落后于领先者一定比例时，给予软性加成（如外交信任回复更快、探索人才成功率略高）。参考 `v4-conquest-pressure.md` §5 末尾「反霸权机制」方向（该报告未实验，仅作方向）。
  - 方向 2：**外交合纵真实化**——弱方更能拉同盟（把「结盟抗强」从 Prompt 口号变成有系统回报的路径）。
  - 方向 3：**不均衡本身作为可调难度/剧本**——提供「历史剧本（原样）」与「均衡剧本（同起点）」两种模式，评测用后者，观赏用前者。
- **评测口径建议**：主理人在评测文档中**明文声明**「开局不均衡是剧本变量，跨模型对比须同势力同 seed」。这样缺口 5 从「缺陷」转为「已声明的设计变量」。

### 6.2 机制定义（若采纳方向 1/2）

- 玩家/LLM 无需感知新命令——补偿是**被动规则**（在回合结算时施加）。
- 交互：LLM 的决策质量体现在「能否利用补偿窗口翻盘」。

### 6.3 可感知反馈

- 事件流出现「【天命】汉室势颓，四方人心思变」类叙事 + 数据面板显示补偿状态。
- 观众能看出「弱者正在被托举」，翻盘有过程感。

### 6.4 与现有系统的接口

| 依赖 | 位置 |
|------|------|
| 城数统计 | `engine.py:1382` `city_counts`（`_check_victory` 内） |
| 外交信任 | `game/systems/diplomacy_relation.py`、`diplomacy_system.py` |
| 探索 | `general_system.py:129` `explore` |
| 产出加成 | `engine.py:840` `get_production_bonus`（已有王国加成通道可复用） |

### 6.5 可插拔性评估 🔴

- **纯数据/口径部分**：零代码，改文档即完成。
- **被动补偿规则**：需要**回合相位钩子**（§6，与缺口 2/4 共用），注册到 `turn_end`。
- **新剧本模式**：属于配置层（`game/game_mode.py` 已有 `GameMode` 枚举），可扩展。

### 6.6 代价与风险

| 项 | 评估 |
|----|------|
| 改动量级 | 口径：零；补偿机制：中（需钩子 + 平衡实验） |
| 是否动战力平衡 | 会（补偿强度敏感） |
| 回滚成本 | 低到中 |
| 风险 | 补偿过度 → 抹平「强方优势」，使策略深度下降；需实验标定强度 |

### 6.7 优先级建议

**决策优先、实施次之。** 建议主理人**先拍板口径**（是否承认「不均衡=剧本变量」），口径一定，缺口 5 的「缺陷成分」即消失。补偿机制随后按需立项。
