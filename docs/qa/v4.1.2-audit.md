## 0. 结论摘要（先给答案）

**一句话：工程骨架扎实，但命令层缺统一归属校验，导致 4 个可被 LLM 直接触发的越权漏洞。**

| 维度 | 结论 | 证据 |
|------|------|------|
| 测试健康度 | ✅ 696 passed / 1 skipped | 实跑 `pytest tests/ -q` |
| 类型健康度 | ✅ 0 error | 实跑 `web/node_modules/.bin/tsc --noEmit` |
| API 可用性 | ✅ 4/4 返回 200 | 实跑 uvicorn + curl 冒烟 |
| 运行时性能 | ✅ 91.7 ms/回合，RSS +3.4 MB/48 回合 | 实跑 12 方 48 回合真实链路 |
| **逻辑正确性** | ❌ **4 个 P0 越权漏洞全部实跑成立** | 见 §3.1，附完整复现输出 |
| 测试有效性 | ⚠️ 覆盖与漏洞区高度互补 | `engine.py` 未覆盖的 270 行，恰好是漏洞所在 |

**破坏性最强的一条**：`explore` + `reward` 两条命令组合，可在**一回合内掏空任意敌国金库**（实测 5000 → 0），己方零支出。这条让整个经济决策层失效 —— GDP 不是被打没的，是被记账记没的。

**根因不是"写错了"，是"没人测到"**：
`engine.py` 覆盖率 63%，其中 `_execute_explore` 的成功分支（第 662–679 行）**完全不在任何测试覆盖内**。696 个测试全绿，是因为没有任何一个测试从"对手视角"构造过命令。


### 1.3 核心循环（Core Loop）

| 层级 | 时长 | 玩家在做的事 |
|---|---|---|
| **Moment-to-moment** | 0.8s/帧 | 看地图上军队移动、战斗闪光、决策理由滚动 |
| **Session loop** | 20–40s/回合 | 12 方各自出招 → 观众读每方决策理由 → 看结果 → 预判下一回合 |
| **Long-term** | 48 回合（184–195 年） | 势力消亡、版图重划、战绩榜累积 |

**Fun Hypothesis（本项目成立的地基）**：
> 好玩的核心是 —— **看一群 LLM 各自带着角色偏见做决策，并把这个决策过程明明白白摊给观众看。**

这条假设决定了两件事，也是本次审计的判据来源：

1. **AI 必须"守规矩"**。观众是在评价模型智能，一旦任何一个势力能通过规则漏洞获益（掏空敌国金库、眼看敌方战俘替自己打仗），"智能对比"就变成"漏洞利用大赛"，**整个项目的产品价值归零**。这是我把越权类问题全部定 P0 的原因，不是因为它们难修。
2. **状态和决策必须对得上**。这个游戏的本质是观演，任何"显示成功但实际未生效"（如 §3.2 的 rumor）都在直接骗观众。

### 1.4 既有的良好工程实践（值得保留，别改坏）

- **确定性**：用 `(priority, seq)` 双键排相位、`(command, id)` 定主将、`(q,r)` 排序浮点求和 —— 这些都是对抗"set 迭代顺序"的工程手段，实测 48 回合可复现。
- **相位钩子 + 命令注册表 + 事件总线**三个扩展点已文档化并做了「平行清单」一致性测试（19 例）。
- **拒绝静默降级**（`load_state_snapshot` 显式抛 `NotImplementedError`）—— 这条原则写进了代码注释。可惜在 `_init_hex_map` 没守住，见 §3.2 P1-5。
- **前后端 XSS 面干净**：`innerHTML`/`dangerouslySetInnerHTML`/`eval` 全仓 0 命中，LLM 产出的 reasoning 走 React 文本节点默认转义。

## 3. 缺陷清单

分级定义：
- **P0**：可被 LLM 在正常游戏流程中触发，破坏/product/公平性或经济体系 → 立即修
- **P1**：导致功能失效、体验断裂或性能劣化 → 本迭代修
- **P2**：一致性、健壮性、可维护性债 → 排期修

### 3.1 逻辑正确性 · P0（越权四件套）

> **共同根因**：`GameEngine` 的 9 个 `_execute_xxx` 各自手写校验，`develop/recruit/attack` 三方有 `city.faction != cmd.faction` 校验，而 **explore / reward / attack(省略分支) 漏了**。没有统一的所有权校验层。

---

#### P0-1 ❌ `reward` 不校验将领阵营，可从敌方国库付款

- **位置**：`game/engine.py:623-650`
- **现象**：`_execute_reward` 全程不判断 `general.faction == cmd.faction`；支付城市由 `general.location` **反推**（632-638 行），逻辑是"谁被赏赐，就花谁所在城市的钱"。
- **实跑证据**（构造：己方洛阳，敌方巨鹿，各 5000 金）：

```
step1 explore: 发现了人才【徐庶】！统帅82，政治78，勇武68，智力90，忠诚88
step2 reward : success=True | 赏赐徐庶 5000金，忠诚度+12
金币: 己方 洛阳 5000 -> 5000 | 敌方 巨鹿 5000 -> 0
>>> 【❌ 缺陷成立】敌国金库被掏空，己方零支出
```

对照组（不经 explore，直接赏敌方现役将刘备）：`敌城金币: 5000 -> 0 | 忠诚 100`。

- **影响**：**经济系统的 source/sink 平衡被彻底击穿**。单个势力一回合内可用一次命令把任意敌城的国库清零，对方的征兵/赏赐/外交全部停摆；同时对 Money supply 没有任何产出关系 —— 这是一个攻击可行、收益无限、成本为零的动作，博弈论里叫 dominant strategy，平衡讨论在此终止。
- **修复思路**：在 `_execute_reward` 增加两道校验：`general.faction == cmd.faction`，以及支付城市 `city.faction == cmd.faction`。更彻底的做法是把校验抽成 `assert_owns(actor, target)` 辅助函数，9 个命令统一调用（见 P0-4）。
- **预期收益**：经济层恢复可信。同时单点修复成本 ≈ 6 行 + 一组回归测试。

---

#### P0-2 ❌ `explore` 不校验城市归属，可把己方将领写进敌城守将名单

- **位置**：`game/engine.py:652-690`（全程只查 `city is None`）
- **实跑证据**：

```
success=True | 发现了人才【徐庶】！...
敌城 巨鹿(julu) 守将列表: ['liu_bei'] -> ['liu_bei', 'explored_54']
注入的将: id=explored_54 名=徐庶 阵营=caocao location=julu
>>> 【❌ 缺陷成立】己方将领被写入敌城守将名单
```

- **影响**：`battle_scheduler.py:206-212` 直接用 `target_city.generals` 计算**守方**平均统帅/勇武/智力，并生成 `defender_general_ids`。敌方城市被注入我方奸细后：
  1. 我军将领被当作"守将"计入防守属性 → 战斗结算被污染；
  2. 打起来时我方奸细会被当作守将**俘虏**，整条投降/占领链被污染。
  这是一次"看起来只是在敌方发现人才"的操作，实际是把探针插进了对方的战斗数值层。
- **修复思路**：补 `city.faction != cmd.faction` 归属校验，与 develop/recruit 一致。
- **预期收益**：战斗数值恢复可信。4 行。

---

#### P0-3 ❌ `attack` 对"location 恰为出发城"的将领跳过阵营与战俘校验

- **位置**：`game/engine.py:529-559`，判定入口 `if general.location != from_city.id:`
- **现象**：`general.faction == cmd.faction` 与 `not general.is_captured` 这两条校验**只写在"异地调将"分支内（541-546）**。若将领 `location == from_city.id`（最常见的场景），这两条校验被整个跳过，只剩一个 `general is None` 检查。
- **实跑证据**（构造：刘备以战俘身份`is_captured=True`滞留在曹操的洛阳）：

```
success=True | 军队 army_1 从 luoyang 出发，目标 julu，距离 2 回合
刘备: faction=liubei is_captured=True location=army_1
>>> 【❌ 缺陷成立】敌方战俘领己方兵出征
```

对照：当战俘的 location 不在出发城时，走 `!=` 分支被正确拒绝（`将领 liu_bei 不在 luoyang`）。**同一个校验，两种命运，取决于将领碰巧站在哪座城。**

- **触发路径真实存在**：`engine.py:1226-1229` 宁死不降的俘虏被移出 `city.generals`，但 `location` 仍残留为该城 id；该城被攻占后，这名敌将就落在己方城里。
- **影响**：敌方囚犯为本方领兵出征，其统帅/勇武/智力计入**攻方**属性（`battle_scheduler.py:239-252`），且 `loyalty_combat_factor` 用的是敌将忠诚度。LLM 只要复述一个它"见过"的将领 id 就能触发 —— 而在 48 回合里，模型复述敌将名是高概率行为。
- **修复思路**：把两条校验提到分支之外做统一前置，不要依赖"是否需要调将"这个偶然条件。
- **预期收益**：战斗归属恢复正确。≈ 4 行。

#### P0-4 ❌ 探索无冷却 + 人才池环形复用 → 无限刷将、重复人物

- **位置**：`game/engine.py:652`（无冷却）；`game/systems/general_system.py:146-149`（`index % 20`）
- **实跑证据**（己方城连续探索 300 次）：

```
常量 EXPLORE_COOLDOWN_TURNS = 3        ← 常量存在
连续探索 300 次 -> 新获武将 109 名（将领总数 53 -> 162）
该城 generals 列表长度: 112

探索得将 109 名；去重后 20 名
重复人物: ['徐庶','法正','庞统','姜维','魏延','张辽','徐晃','张郃','于禁',
          '乐进','甘宁','吕蒙','陆逊','周泰','凌统','黄忠','王平','廖化','李严','邓艾']
```

另证实：**全仓没有任何每回合命令数的代码层上限**（`grep max_commands|commands_per_turn|MAX_COMMANDS` 零命中）—— 数量约束只存在于 LLM 提示词里。

- **影响**：
  1. `EXPLORE_COOLDOWN_TURNS = 3` 定义了但从未接线，是本项目高频失效族「定义了但从未执行」的第 N 例；
  2. 人才池 20 人耗尽后按 `index % 20` 环形取用 → **同一局内出现 5 个徐庶、5 个法正**，观众眼里的"名将"变成批发货，史实代入感直接崩掉；
  3. 结合 P0-1，无限探索 + 无限赏赐 = 无限榨干任意敌方国库。
- **修复思路**：① 把 `EXPLORE_COOLDOWN_TURNS` 接进 `_execute_explore`（在 city 上记 `last_explore_turn`）；② 人才池耗尽后返回 `found=False`；③ 在 `_execute_explore` 入口加单城每回合一次调用上限。
- **预期收益**：武将作为稀缺资源的价值回归，叙事可信度恢复。

### 3.2 逻辑正确性 · P1

#### P1-1 ⚠️ 守军上限在三路径中被绕过

- **位置**：有 cap：`city_system.py:225`（征兵）、`engine.py:1405`（解散军入城）；无 cap：`army_movement.py:351`（援军到达）、`battle_scheduler.py:178`、`engine.py:1172`
- **实跑证据**（洛阳 level=4，上限 4000）：

```
A 征兵路径    : garrison=4000 超限=False  -> 被截断 ✅
B 援军到达路径: garrison=9000 超限=True   -> 绕过 ❌
```

- **影响**：`GARRISON_CAP_PER_LEVEL` 是围城攻防平衡的**唯一锚点**。围城伤害公式 `WALL_DAMAGE_FORCE_MULTIPLIER_CAP`（`battle_resolver.py:339-343`）以 `attacker/garrison` 计算 —— 把守军堆到上限之外，就能让任何攻城变成必败。这是典型的 passive structure-blocking exploit：不用出手，只靠堆兵就能锁死版图。48 回合实测 HHI 只有 0.199（规则 AI），与这类"僵持化"结构性因素有关。
- **修复思路**：抽出 `add_garrison(city, n)` 统一方法做 `min(...)` 截断，三条入口全部调用。
- **预期收益**：攻防平衡恢复已验证的阈值（兵力 ≥守军 1.25× → 胜率 100%）。

#### P1-2 ⚠️ LLM 模式下 `reasoning` 让 WS 载荷突破性能基线 4 倍

- **位置**：`api/server.py:241`（`send_state` 从不传 `reasoning_limit`）；`api/game_manager.py:409-494`
- **实跑证据**（中局状态，489 字符/条的样本）：

| reasoning 条数 | `/api/state` 载荷 | 超 75 KB 基线？ |
|---|---|---|
| 0 | 67,337 B (65.8 KB) | 否 |
| 20 | 78,835 B (77.0 KB) | **是** |
| 50 | 96,085 B (93.8 KB) | **是** |
| 100 | 124,835 B (121.9 KB) | **是** |
| 400（满档） | 297,627 B (290.7 KB) | **是** |

每条 reasoning 约摊 576 B，400 条满档追加 230 KB。

- **影响**：**这正是刚做完的 hex_map 瘦身（2.34 MB → 63 KB）的对立面，且只在 LLM 模式下爆发。** 规则 AI 下 reasoning 恒为 0，所以它只在真实 LLM 对局中爆发，测试永远测不到 —— 这是「696 测试全绿却抓不到」的典型。前端 `Panel.tsx:503` 还对该列表做全量渲染，DOM 节点数与滚动成本同步上涨。
- **修复思路**：WS 的 `send_state` 按前端当前 Tab 决定是否下发 reasoning；非「决策」Tab 时传 `reasoning_limit=0`，切到该 Tab 时用 REST 按需拉取历史。这样干既能控载荷又不丢功能。
- **预期收益**：自动推进下的每帧流量回到 ~63 KB（降 78%），与既有性能基线对齐。

#### P1-3 ⚠️ WS 处理器同步调用阻塞式 `process_turn`，占死 asyncio 事件循环

- **位置**：`api/server.py:294`（`next_turn`）、`api/server.py:250`（`auto_loop`）、`api/server.py:289`（`command`）
- **证据（静态确认）**：三处均为 `async def` 内直接调用**同步** `_manager.process_turn()`；全仓 `grep run_in_executor|to_thread` **零命中**。`game_manager.py:141-143` 自述「LLM 模式下单回合 12 方约 40 秒」。
- **影响**：单回合 40 秒期间事件循环完全停摆 —— ① 用户点「停止自动推进」要等**整整一个回合**才生效；② ping/pong 无响应；③ 同进程的其它标签页/REST 请求排队饿死。**这是用户最直观感受到的"卡死"，而 tp/root cause 只有一行。**
- **修复思路**：`await asyncio.get_running_loop().run_in_executor(None, _manager.process_turn)`；`auto_loop` 加「上一回合未完成则跳过本 tick」的闸门。
- **预期收益**：UI 从"回合级响应"回到亚秒级响应。改动量 3 行。

#### P1-4 ⚠️ 自动推进状态三方错位，`auto` 永不回落

- **位置**：`api/server.py:246-249`（`if game_over: break`，break 前不发任何消息）；`api/server.py:234`（`auto_task` 是**连接级局部**变量）；前端 `useGame.ts`（重连不补发 `{type:'auto'}`）
- **证据（静态确认）**：后端 game_over 后静默 break，前端收到 `game_over=true` 却无任何 `useEffect` 复位 `auto`；WS 重连后新协程 `auto_task=None`，而 `connect()` 只 `new WebSocket`。
- **影响**：界面永久显示「自动推进中」，而「下一回合」「空格」因 `App.tsx:138 disabled={auto || thinking}` **永久禁用**，实际后端一步没在推进。用户只能手动点「停止」自救。这直接违反本项目"不做假控件"的既定纪律 —— 一个到处显示正在运行、实际已死的开关，比不显示更糟。
- **修复思路**：后端 break 前发 `{"type":"auto_stopped"}`；前端 `onopen` 按当前 `auto` 补发；`useGame` 加 `useEffect(() => { if (state?.game_over) setAuto(false) }, [state?.game_over])`。
- **预期收益**：消除一个用户必然遇到且完全无法自解释的状态。

#### P1-5 ⚠️ `_init_hex_map` 的裸 `except Exception` 静默降级为「无地图模式」

- **位置**：`game/engine.py:269-316`（尤其 313-316）
- **现象**：`try` 包住地图生成 + 领地初始化 + 影响力初始化的全部代码，任何异常只 log warning，然后 `self.hex_map = None`。
- **证据**：`coverage report -m` 显示第 **313-316** 行正在未覆盖清单里 —— 这条降级路径 **从未被任何测试走过**。
- **影响**：一旦触发，整个 section 走 `process_turn:927` 的 else 分支，地块产出/领地/寻路/六角路径校验全部消失，游戏**照常运行但规则完全不同**。这与项目自己在 `load_state_snapshot` 里写下的「拒绝静默降级」原则相矛盾。
- **修复思路**：fail fast 重抛，或把降级写进 `result` 并在 UI 显著提示；至少把 `except` 收窄到"地图数据缺失"这一类可预期错误。

#### P1-6 ⚠️ `rumor` 无 `target_general` 时完全空转却返回 success=True

- **位置**：`game/engine.py:726-750` + `game/systems/diplomacy_system.py:167-219`
- **现象**：不带 `target_general` 时走 else 分支，**只返回一句文案**；该函数从未拿到 `City` 对象（engine 也没传），因此 `city.morale` 不可能被改动。另：`target_general` 不经阵营判断 → **可对自家将领散布流言**（连续 6 次把曹操忠诚 95 → 65），同时每次判定消耗 `self._rng.random()`，污染确定性 RNG 序列。
- **影响**：球员/LLM 每回合消耗一次行动却零状态变化，且**系统谎报成功**。对一个靠"把决策摊给观众看"的作品来说，这是直接的信息污染 —— 观众看到"流言成功"，实际什么都没发生。
- **修复思路**：要么实现「对城施流言 → 民心下降」，要么在无 `target_general` 时返回 `success=False`；同时加"目标必须是非己方"校验。

## 4. 根因分析：为什么 696 个测试全绿，P0 却能活到发布

不是一个 bug 跑出去了，是**测试策略与失效模式错位**。三个原因，按贡献度排序：

| # | 原因 | 证据 |
|---|---|---|
| 1 | **没有 adversarial 用例** —— 所有测试验证"我能做什么"，没有验证"我不该做什么" | 4 个 P0 全部可用非所有者身份触发，无一条断言覆盖 |
| 2 | **校验逻辑没有单一 choke point** —— 9 个命令各写各的，漏一个没人发现 | 三方有归属校验、三方没有，差异写在工作량里不在架构里 |
| 3 | **测试全是规则 AI** —— LLM 路径的行为（reasoning 累积、reward cost）在测试里恒为空/默认值 | P1-2 载荷超标 4 倍，规则 AI 下永远测不出来 |

这也是本项目历史上反复出事的同一族（俘虏链、民心规则、trust、TRUCE）：**「代码读起来是齐的，但这段代码从未真正跑过」**。这一次，「从未跑过」的位置换成了「从未被测过」。

**建议写进准入纪律的最小一条**（投入产出比最高）：

> 每新增或修改一个 `_execute_*` 命令，必须同时提交一条「非所有者调用 → `success=False`」的断言。

这条大概能拦住本族未来 80% 的问题，成本是每人次 10 分钟。

## 5. 游戏设计层建议

作为设计师，除了修 bug，还有三条会影响"这游戏好不好看"的建议。都与一个前提有关：**本项目不是策略游戏，是"围观台"** —— 判据不是"玩家爽不爽"，而是"观众能不能看懂 LLM 在想什么、能不能看出高低"。

### 5.1 「决策可见性」是核心价值，但现在被三件事稀释

| 现象 | 来源 | 建议 |
|---|---|---|
| `reasoning` 和 войной 决策对不上：写着"流言成功"但实际零效果 | P1-6 | 先修假成功；**凡是 success=True 的命令必须在 state 里留下可观测痕迹**，否则一律返回 False |
| 说好的称帝有惩罚，实际是纯增益 | P2-4 | 二选一，不要留壳 |
| 同盟是单方面即刻成立，看不到谈判 | P2-4 | 接 `propose_alliance`，让"提议→等待→拒绝/接受"成为可见的一回合事件 |

同盟拉扯这条值得一做：**观众想看的正是 LLM 之间互相说服的过程**，而现在 code path 直接跳过了它。这可能是投入最小、对核心卖点提升最大的一处的改变。

### 5.2 资源稀缺性不足 → 决策没有张力

实跑 48 回合（规则 AI）：总兵力从 45,400 涨到 70,255（+55%），存活势力 13 → 9，HHI 仅 **0.199**。这意味着**兵只会越来越多，而 makan لاlections 不会变难** —— 与玩家反馈的"经济/兵力上限太紧"看似矛盾，实际是同一个问题的两面：**开局紧，中期松**。

作为 **v4.2 的 tuning 议题**建议引入一个明确的 sink：`军队维持成本随总兵力超线性增长`（如超过阈值后 `food_consumption ∝ n^1.15`）。rationale：让"扩张到什么程度必须转为开发"成为每回合的真决策，而不是"永远继续招兵"。数值一律标 [PLACEHOLDER]，需 exp20 对照实验（有 sink vs 无 sink 的 HHI 曲线）标定后入库。

### 5.3 州郡层差异化（既有待办，优先级建议上调）

记忆里玩家第一条反馈是「不能突出各派系、各城市、各州县之间的特点与差异」—— v4.1.2 已完成**势力层**（相性/硬禁/信任档），但**州郡层完全未动**。当前 31 座城在数值上只有 level 不同，地理只影响寻路距离。

建议的最小可行版本：给每个州一个单一的生产 modifiers（如司州 +钱 / 益州 +粮 / 凉州 +兵 / 交州 -everything），让"抢哪个州"在开局就有非对称答案。这比新增系统便宜得多，且能立刻改善"每个城看起来都一样"。
