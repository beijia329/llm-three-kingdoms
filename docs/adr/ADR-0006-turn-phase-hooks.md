# ADR-0006 回合相位钩子（Turn-Phase Hook Registry）

- **状态**：Accepted（已落地）
- **日期**：2026-10-03
- **相关**：ADR-0001（三层分离）、ADR-0002（确定性）、ADR-0004（多级容错）、
  `game/turn_phase.py`、`game/engine.py:process_turn`、
  `docs/design/v4.1-gameplay-gaps.md`（需求来源）

---

## 背景（Context）

`GameEngine.process_turn` 原是一条**硬编码固定序列**：

```
外交到期 → 资源产出 → 影响力扩散 → 行军推进 → 收容撤退军 → 人设代价
→ 忠诚衰减 → 战斗结算 → 清理死军 → 胜利判定 → 建国检测 → 回合递增
```

任何「每回合要结算的新机制」都必须**改动这个函数本体**。design-strategist 的
`v4.1-gameplay-gaps.md` 从 5 个玩法缺口反推出：缺口 1/4（主动）可挂**命令注册表**、
缺口 3 可挂**事件总线**，而**缺口 2（真围城的逐回合损耗）与缺口 4/5 的被动部分，
必须挂一根新钩子——回合相位钩子**。这是「加玩法成本高」的结构性根因。

时机判断：当真实用例积累到 2–3 个（围城逐回合结算 / 经济出口 / 弱方被动加成）后，
契约即可**从需求反推**，而非凭空设计——满足「Rule of Three」，不再是过早抽象。

---

## 决策（Decision）

### 1. 相位划分

定义 5 个相位（`TurnPhase`），覆盖「新机制可能想挂的位置」，引擎在 `process_turn`
内按 `PHASE_ORDER` 顺序触发：

| 相位 | 触发点 | 典型用途 |
|---|---|---|
| `turn_start` | 季节/年份更新后、外交到期前 | 回合开场逻辑 |
| `after_production` | 资源产出后、行军前 | 影响力扩散（已迁） |
| `after_movement` | 行军+收容撤退军后、忠诚衰减前 | 人设代价（已迁） |
| `after_resolution` | 战斗结算+清理死军后、胜利判定前 | 战后结算 |
| `turn_end` | 回合递增后、写日志/广播前 | 回合收尾 |

### 2. 注册表有序且确定

`register_phase_hook(phase, fn, *, priority=100, name=None)`；执行顺序按
**(priority, 注册序 seq)** 双键排序。**绝不依赖 dict/hash 迭代序**——本项目已有 3 次
「集合迭代序非确定性」事故（见 `docs/audit/2026-10-determinism-set-iteration-scan.md`）。

### 3. 钩子失败策略：记录 + 继续 + 可观测

钩子抛异常时：**`logger.exception` 记录 → 写入 `result["hook_errors"]` → 继续执行后续钩子**，
**不中止整局**。

理由：
- 一个 mod/新系统的 bug **不应让整局崩**——与 ADR-0004「游戏必须跑到结束」一致；
- **但必须可观测**：写进 `result["hook_errors"]` 且打日志，**绝不静默吞掉**
  （本项目反复栽在「静默兜底掩盖真问题」上：`getattr` 兜底、`except: pass`）。
- 为什么选「继续」而非「中止」：中止会让一个次要系统的错误升级为「整局不可用」，
  代价与收益不对称；而「记录 + 继续」把故障降级为「该机制本回合不生效 + 一条可见错误」。
- `hook_errors` 采用**惰性写入**（无错误时不加该键）→ 保证「零行为变更」。

### 4. 与 EventBus 的分工（不是替代关系）

| | EventBus（ADR-0001） | 相位钩子（本 ADR） |
|---|---|---|
| 语义 | **通知已发生的事** | **在固定时机执行逻辑** |
| 方向 | 发布者广播，不关心谁听 | 引擎保证在确定时机调用注册者 |
| 副作用 | 订阅者被动响应 | 钩子可主动修改状态 |
| 典型用途 | UI/日志感知「战斗结束」「占城」 | 逐回合结算（围城损耗、经济出口） |

一句话：**EventBus 是「事后广播」，相位钩子是「到点执行」。**

---

## 后果（Consequences）

**正面**
- 新增「每回合结算」机制 = `register_phase_hook(...)`，**不再改 `process_turn`**。
- 这是档 A 三根钩子的最后一根（命令注册表 / 事件总线 / 系统相位），三根齐备后
  「加一个玩法系统」才真正是「注册一下」。
- 顺序确定、失败可观测，符合本项目确定性（ADR-0002）与容错（ADR-0004）约束。

**负面 / 风险**
- 相位粒度是**设计约束**：钩子只能挂在 5 个既定相位，不能插到任意语句之间。
  若未来出现需要更细粒度的需求，需扩展相位枚举（属可接受演进）。
- 多钩子同相位时的相对顺序由 priority 决定，**注册者必须理解 priority 语义**，否则可能
  出现隐蔽的顺序依赖。→ 约定：同功能域给同一 priority 区间，避免跨域争序。

## 备选方案（Alternatives Considered）

| 方案 | 结论 |
|---|---|
| 继续硬编码在 `process_turn` | 每加机制都改核心循环，正是要解决的根因。否决 |
| 用 EventBus 承载「逐回合结算」 | 语义不符（事件是「事后通知」）；且钩子需保证「一定被调用」，事件是「发出去就完事」。否决 |
| 通用中间件链（每个 hook 可拦截/改写 result 并决定是否继续） | 过度设计；当前只需「确定时机执行」，不需要拦截语义。否决 |
| 相位更细（每个步骤一个相位） | 相位爆炸、契约不稳；当前 5 个覆盖已知需求即可 |

---

## 落地核查点

- 迁入顺序（**先立标尺再动刀**）：先建注册表+调用点（零行为，指纹应一致）→ 迁
  `influence_system`（验指纹）→ 迁 `nature_strain`（验指纹）→ 全量测试。
- **逐回合指纹必须一致**（`tests/integration/test_cross_process_determinism.py`）。
- 证明模式：注册一个假钩子并断言其在正确相位被调用（`tests/unit/test_turn_phase.py`）。
