## 一、设计理念

### 1.1 核心思想
boardgame.io 不是通用游戏引擎，而是专为回合制、确定性、多玩家异步/同步对战场景深度优化的**状态管理中间件**。

### 1.2 四大设计原则

| 原则 | 说明 |
|------|------|
| **纯函数式游戏逻辑** | 游戏规则是纯函数，相同输入=相同输出 |
| **不可变状态演进** | 每次操作产生新状态，不修改旧状态 |
| **确定性回合推进** | 相同的操作序列产生相同的游戏结果 |
| **服务端权威** | 所有状态变更都经过服务端校验 |

## 二、核心概念

### 2.1 G 与 ctx 分离

**G（Game State）**：
- 开发者管理的游戏状态
- 包含所有游戏数据
- 随游戏进程变化

**ctx（Context）**：
- 框架管理的元数据
- 只读
- 包含：当前玩家、回合数、游戏阶段等

**为什么分离**：
- 游戏逻辑只关心G，不关心框架元数据
- 框架可以统一处理回合切换、胜利判定等
- 状态更清晰，职责更明确

### 2.2 Moves（动作）
玩家操作封装为move函数：
- 输入：G + ctx + 玩家参数
- 输出：新的G
- 纯函数，无副作用

```javascript
function move(G, ctx, ...args) {
  // 修改G
  return G;
}
```

### 2.3 日志与时间旅行
- 所有move都被记录
- 可以回放任意时刻的状态
- 支持Undo/Redo
- 支持状态哈希校验

### 3.2 插件系统
boardgame.io的精髓在于插件系统：
- 事件插件
- 日志插件
- 随机数插件
- 可以自定义插件

**好处**：
- 核心保持简单
- 功能通过插件扩展
- 按需加载，不臃肿

## 四、确定性设计

### 4.1 为什么重要
- 多人游戏：所有客户端看到相同的结果
- 回放：可以精确复现任何一局
- 调试：相同的输入产生相同的bug
- 反作弊：可以校验状态是否合法

### 4.2 如何保证确定性
- 统一的随机数生成器（带seed）
- 固定的执行顺序
- 没有时间依赖
- 没有外部依赖

### 4.3 状态哈希
每个状态计算哈希值：
- 检测状态是否被篡改
- 客户端与服务端校验
- 快速定位差异

## 五、对本项目的启示

### 5.1 我们已经借鉴的
✅ 三层分离架构（Engine/Player/Renderer）
✅ 确定性随机数
✅ 状态快照与回滚
✅ G与ctx分离思想
✅ 事件驱动

### 5.2 可以进一步借鉴的

**命令模式**：
- 所有玩家操作都是Command对象
- 可以序列化、可以回放、可以校验
- 对应boardgame.io的moves

**状态不可变性**：
- 每次操作产生新状态，不修改旧的
- 便于调试和回滚
- 但Python里实现成本较高，可以折中

**插件系统思想**：
- 核心引擎保持简单
- 功能通过子系统扩展
- 我们的子系统设计已经有点这个意思了

**服务端权威思想**：
- 虽然我们是单机，但Engine是权威的
- Player不能直接修改状态，只能发命令
- 我们的三层架构已经体现了
