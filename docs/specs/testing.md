# 测试规范（增强版）

> 本文档定义项目的测试标准和规范。
> 所有开发必须遵守，确保代码质量和游戏平衡性。
> 参考：knowledge-base/testing/ 下的参考资料

---

## 一、测试策略总览

### 1.1 测试金字塔

```
        /\           ← E2E测试（少量）
       /  \
      /----\         ← 集成测试（适量）
     /      \
    /--------\       ← 单元测试（大量）
   /          \
```

| 层级 | 数量 | 速度 | 目的 | 占比 |
|------|------|------|------|------|
| **单元测试** | 大量 | 快 | 验证单个函数/类的正确性 | 70% |
| **集成测试** | 适量 | 中 | 验证模块间协作是否正确 | 20% |
| **E2E测试** | 少量 | 慢 | 验证完整游戏流程 | 10% |

### 1.2 覆盖率要求

| 模块 | 行覆盖率 | 分支覆盖率 | 说明 |
|------|---------|-----------|------|
| 战斗系统 | 90% | 85% | 核心逻辑，必须高覆盖 |
| 资源系统 | 85% | 80% | 经济基础，很重要 |
| 命令解析 | 90% | 85% | LLM输出不可靠，必须测全 |
| 状态校验 | 95% | 90% | 状态合法性是基础 |
| 整体 | 80% | 70% | 最低要求 |

### 1.3 TDD（测试驱动开发）
**核心逻辑必须采用TDD**：先写测试，再写实现。

**TDD三步循环**：
```
1. 红：先写测试，运行测试，确认失败
   ↓
2. 绿：写实现代码，让测试通过
   ↓
3. 重构：优化代码，保持测试通过
```

**为什么TDD**：
- 保证代码可测试（写不出测试说明设计有问题）
- 减少bug（测试覆盖了各种情况）
- 便于重构（有测试兜底，不怕改坏）
- 文档化（测试就是最好的用法说明）

**哪些必须TDD**：
- 战斗系统（伤害计算、士气、战斗流程）
- 资源系统（产出、消耗、民心计算）
- 命令解析器
- 状态合法性校验
- 所有核心算法

**哪些可以不用TDD**：
- GUI渲染（视觉效果，不好测）
- 简单的胶水代码
- 配置和常量

## 二、单元测试规范

### 2.1 测试结构
每个测试文件遵循 AAA 模式：

```python
def test_xxx():
    # Arrange：准备测试数据
    ...
    
    # Act：执行被测试的代码
    result = function_under_test(...)
    
    # Assert：验证结果
    assert result == expected
```

### 2.2 命名规范
测试函数名要清晰描述测试的场景和预期结果。

**格式**：`test_<功能>_<场景>_<预期结果>`

**好的例子**：
```python
def test_calculate_damage_normal_case_returns_correct_value()
def test_recruit_not_enough_gold_raises_error()
def test_battle_attacker_wins_when_stronger()
```

**不好的例子**：
```python
def test1()
def test_damage()
def test_bug_fix()
```

### 2.3 测试分类
每个测试文件按场景分类：

- **正常场景**：正常输入下的正确行为
- **边界场景**：边界值、极值
- **错误场景**：错误输入、异常情况
- **特殊场景**：特殊条件、组合情况

### 2.4 Fixture 规范
- 通用的测试数据用fixture
- fixture要小而专，不要大而全
- 每个测试用自己的fixture，不要共享状态

**例子**：
```python
@pytest.fixture
def sample_city():
    return City(
        name="许昌",
        faction="wei",
        level=3,
        gold=2000,
        troops=5000,
    )

@pytest.fixture
def sample_army():
    return Army(
        faction="wei",
        troops=3000,
        general="曹操",
        morale=80,
    )
```

### 2.5 测试独立性
- 每个测试独立运行，不依赖其他测试
- 测试之间不共享状态
- 测试顺序不影响结果

## 三、战斗系统测试要点

### 3.1 伤害计算测试
- 基础伤害计算
- 统帅加成
- 士气加成
- 地形加成
- 城墙减伤
- 各种组合情况

### 3.2 士气系统测试
- 士气对战斗力的影响
- 士气提升/降低
- 士气为0时的溃散
- 士气恢复
- 低士气的负面效果

### 3.3 战斗流程测试
- 三阶段战斗（围城→破墙→巷战）
- 战斗结束条件
- 胜负判定
- 战后处理（俘虏、占领、伤亡）

### 3.4 边界测试
- 0兵力的战斗
- 兵力相差悬殊的战斗
- 士气为0的战斗
- 城墙满级 vs 0级城墙

## 四、LLM解析器测试要点

### 4.1 正常格式测试
- 标准JSON
- 带markdown代码块的JSON
- 有多余空白的JSON

### 4.2 语法错误测试
- 尾随逗号
- 单引号
- 缺少引号的key
- 截断的JSON
- 各种常见语法错误

### 4.3 语义错误测试
- 缺少必填字段
- 字段类型错误
- 枚举值错误
- 数值范围错误

### 4.4 容错测试
- JSON藏在废话中间
- 多个JSON
- 格式完全混乱的输出
- 空输出

### 4.5 假阳性测试
- json_repair修复后语法对但语义错的情况
- 确保Schema校验能捕获这些错误

## 五、集成测试规范

### 5.1 什么是集成测试
测试多个模块组合在一起是否正常工作。

### 5.2 集成测试范围
- 游戏引擎 + 子系统
- 命令执行 + 状态变更
- 战斗系统 + 军队移动
- LLM玩家 + 游戏引擎

### 5.3 关键集成测试场景

#### 完整回合流程
```
执行命令 → 处理行军 → 处理战斗 → 回合结束 → 胜负判定
```

#### 城市发展链
```
发展城市 → 产出增加 → 征兵更多 → 军队更强
```

#### 战斗链
```
下令进攻 → 军队出发 → 行军 → 到达 → 战斗 → 占领/撤退
```

#### 外交链
```
发送消息 → 对方收到 → 对方决策 → 影响关系
```

## 六、E2E测试规范

### 6.1 什么是E2E测试
测试完整的游戏流程，从开始到结束。

### 6.2 E2E测试场景

#### 完整一局游戏
- 初始化游戏
- 运行N回合
- 验证游戏正常结束
- 验证有获胜方

#### 多局稳定性测试
- 连续跑10局
- 验证不会崩溃
- 验证每局都能正常结束

#### 确定性测试
- 用相同的seed跑两局
- 验证结果完全一致
- 验证状态哈希相同

## 七、平衡性测试

### 7.1 平衡性测试方法

#### 蒙特卡洛模拟
- 批量运行随机对局
- 统计各项指标
- 分析分布

#### 参数扫描
- 系统调整关键参数
- 观察胜率变化
- 找到平衡点

#### 极端策略测试
- 测试各种极端策略
- 确保没有OP策略
- 确保游戏有多种玩法

### 7.2 平衡性指标

#### 胜率分布
- 三方胜率是否接近
- 理想：各33%
- 可接受：25%-40%
- 不合格：某方 > 50% 或 < 15%

#### 游戏时长
- 平均回合数：20-30回合
- 最短：不少于10回合
- 最长：不超过40回合

#### 战斗胜率
- 进攻方胜率 vs 防守方胜率
- 理想：接近50/50
- 可接受：40%-60%

#### 资源平衡
- 金钱 vs 粮草的价值
- 经济发展 vs 军事扩张的收益
- 确保两种路线都可行

### 7.3 极端策略清单

| 策略 | 描述 | 预期胜率 |
|------|------|---------|
| 速攻流 | 开局爆兵，快速进攻 | 30-40% |
| 龟缩流 | 只守不攻，堆防御 | 20-30% |
| 经济流 | 全力发展，后期一波 | 30-40% |
| 流言流 | 只放流言，不打仗 | 15-25% |
| 集中流 | 所有兵力打一个方向 | 30-40% |

**判断标准**：没有任何策略胜率 > 50%

### 7.4 平衡性调优流程

```
1. 跑基准测试（当前参数跑1000局）
   ↓
2. 分析问题（哪方太强？哪种策略OP？）
   ↓
3. 假设原因（是城墙太强？还是资源产出太高？）
   ↓
4. 调整参数（小幅度调整，每次1-2个）
   ↓
5. 跑测试验证（再跑1000局）
   ↓
6. 分析结果（有没有改善？有没有副作用？）
   ↓
7. 采纳或回滚
```

## 八、测试工具与配置

### 8.1 测试框架
- **pytest**：主测试框架
- **pytest-cov**：覆盖率统计
- **pytest-xdist**：并行测试

### 8.2 测试目录结构
```
tests/
├── unit/                    # 单元测试
│   ├── test_engine.py
│   ├── test_battle.py
│   ├── test_resource.py
│   ├── test_city.py
│   ├── test_general.py
│   ├── test_command_parser.py
│   └── ...
├── integration/             # 集成测试
│   ├── test_full_turn.py
│   ├── test_battle_flow.py
│   └── ...
├── e2e/                     # E2E测试
│   ├── test_full_game.py
│   └── test_determinism.py
├── balance/                 # 平衡性测试
│   ├── test_monte_carlo.py
│   ├── test_extreme_strategies.py
│   └── parameter_scan.py
└── conftest.py              # pytest配置
```

### 8.3 运行测试
```bash
# 运行所有测试
pytest

# 运行单元测试
pytest tests/unit/

# 运行特定文件
pytest tests/unit/test_battle.py

# 查看覆盖率
pytest --cov=game --cov-report=html

# 并行运行
pytest -n auto
```

## 九、测试最佳实践

### 9.1 写好测试的原则
1. **每个测试只测一件事**：出了问题一眼就知道哪里错了
2. **测试要独立**：不依赖其他测试的状态
3. **测试要快**：单元测试应该毫秒级完成
4. **测试要可读**：别人看测试就能理解代码做什么
5. **测试要完整**：正常、边界、错误都要覆盖

### 9.2 什么时候写测试
- **新功能**：先写测试，再写实现（TDD）
- **修bug**：先写测试复现bug，再修复
- **重构**：确保有测试覆盖，再重构
- **复杂逻辑**：必须有充分的测试

### 9.3 测试不是越多越好
- 测试也要维护，太多了维护成本高
- 重点测试核心逻辑和容易出错的地方
- 简单的getter/setter不用测
- 配置和常量不用测

### 9.4 测试的"味道"
出现以下情况，说明设计可能有问题：
- 写测试很难
- 一个测试要mock很多东西
- 测试比实现代码还长
- 改一个功能要改好多测试

→ 这时候应该反思设计，而不是硬写测试。

## 十、提交前检查清单

提交代码前，确保：

- [ ] 所有单元测试通过
- [ ] 新功能有对应的测试
- [ ] bug修复有回归测试
- [ ] 核心逻辑覆盖率 > 80%
- [ ] 测试是独立的，不互相依赖
- [ ] 测试命名清晰，描述准确
- [ ] 测试运行速度合理
